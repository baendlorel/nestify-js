8. JWT 过期时间边界及类型校验不正确
位置：packages/core/src/auth/jwt.ts:181
复现：expiresIn 为 1 秒时，恰到 exp 秒的令牌仍被接受。代码同时用真值判断 exp，因此 exp=0 不会检查；也没有验证 exp 是有限数字。
影响：过期或无效的时间声明可能被接受。
建议：严格校验声明类型，在 now >= exp + tolerance 时拒绝，并覆盖边界和无效值。

9. DI 以类名代替类身份，导致不同类发生 token 冲突
位置：packages/core/src/register/lazy-injector.ts:34、packages/core/src/register/provider.ts:30、packages/core/src/register/provider.ts:76
复现：两个不同的 class Service 同时注册时，第二个类的查找返回第一个类的实例。
影响：跨模块、第三方库或构建压缩产生同名类时，注入错误实例，甚至引发错误的权限或业务行为。
建议：类 token 使用构造函数身份；字符串和 symbol token 保持独立。

10. 模块隔离可以被 Symbol 字段和 useExisting 绕过
位置：packages/core/src/register/expect-module.ts:198、packages/core/src/register/lazy-injector.ts:113、packages/core/src/register/lazy-injector.ts:137
复现：未导出、未导入的兄弟模块 provider，既可通过 Symbol 名字段 @Inject 注入，也可通过 useExisting 别名访问。
原因：依赖检查使用 Object.values，漏掉 Symbol 属性；useExisting 不参与依赖可访问性检查，而实例 map 是应用级共享。
建议：遍历所有自有键，并对别名目标执行同样的模块可访问性验证。

11. factory 依赖按声明顺序取值，缺失时静默传入 undefined
位置：packages/core/src/register/module.ts:46、packages/core/src/register/lazy-injector.ts:107、packages/core/src/register/lazy-injector.ts:129
复现：providers 中 factory 排在其注入的类之前时，factory 收到 undefined；注入默认 APP_LOGGER 的 factory 也收到 undefined，因为默认 logger 在之后的 apply 阶段才加入。
此外，factory 即使拿到类实例，该实例的字段注入也尚未完成。
建议：按依赖图初始化 factory，确保依赖及字段注入就绪，对缺失和循环依赖明确报错。

中
==

12. 默认异常处理把内部错误作为 400 并暴露原始消息
位置：packages/core/src/register/route/middlewares/filter.ts:16
复现：控制器抛出普通 Error 时响应状态为 400，body 包含原始 error.message。
影响：服务端故障被误报为客户端错误，内部实现或敏感信息可能返回给客户端。
建议：未知异常记录服务端日志，返回不泄露细节的 500；保留显式 HttpException 的语义。

13. JwtGuard 对缺失或无效令牌返回 400 而不是 401
位置：packages/core/src/auth/jwt.guard.ts:47、packages/core/src/auth/jwt.guard.ts:59
复现：受保护路由不传 Authorization 返回 400。验证时的 UnauthorizedException 也被重新包装成普通 Error。
建议：抛出或保留 UnauthorizedException，不要把身份验证失败降级为普通错误。

14. 异步 factory 注入的是 Promise 而不是其结果
位置：packages/core/src/register/lazy-injector.ts:107
复现：useFactory: async () => 'ready' 后，依赖字段收到 Promise。
类型允许 factory 返回任意值，但初始化过程不会等待它。若异步 factory 不在设计范围内，至少应明确拒绝或文档化，避免静默注入错误类型。

15. useExisting 无法引用基本类型的 useValue
位置：packages/core/src/register/lazy-injector.ts:113
复现：{ provide: 'value', useValue: 1 } 再加 { provide: 'alias', useExisting: 'value' }，启动时报找不到 provider。
原因：只接受对象实例，而 useValue 允许任意值；createInstance 的去重也只识别对象值。
建议：使用 Map.has 判断是否存在，保留 false、0、字符串、null 和 undefined 等已注册值。

16. 拦截器 catch 无法捕获控制器或 pipe 抛出的异常
位置：packages/core/src/register/route/handler.ts:30、packages/core/src/decorators/middlewares/interceptor.ts:26
复现：拦截器注册 next.catch 后，控制器抛错，catch 回调没有执行，直接进入 filter。
当前 catch 仅覆盖该拦截器自身 map/tap 回调中的异常，不能覆盖其包装的下游处理流程。
建议：明确并实现拦截器对下游错误的传播和恢复语义。

17. 叠加多个同级中间件装饰器会相互覆盖
位置：packages/core/src/register/meta.ts:214、packages/core/src/register/meta.ts:278、packages/core/src/decorators/middlewares/pipe.ts:70
复现：同一 handler 叠加两个 @UsePipes，只有最外层的 pipe 执行。其他 UseGuards/UseFilters/UseInterceptors 同样直接覆盖元数据。
@Body、@File 等也通过 UsePipes 写入同一位置，和另一个方法级 pipe 装饰器组合时可能被覆盖。
建议：合并同级声明并明确执行顺序；覆盖情况需有文档和测试。

18. Cron 按函数身份去重，误丢弃不同实例上的相同方法
位置：packages/core/src/schedule/cron.ts:143、packages/core/src/schedule/cron.ts:157
复现：为同一类的两个实例调用 bindCronJob 后，仅注册一个任务，因为实例共享原型方法函数。
建议：以实例和方法的组合去重，只折叠同一实例的重复别名。

19. Cron 执行过程中停止再启动会产生重复计时器
位置：packages/core/src/schedule/cron.ts:75、packages/core/src/schedule/cron.ts:92、packages/core/src/schedule/cron.ts:167
复现：任务仍在 await 时 stop、start，再让原任务完成；下一秒处理函数执行两次。
原因：restart 已安排新计时器，而旧执行的 finally 又看到 running=true 并再次安排。
建议：使用执行代次或取消标记，保证旧执行不能为新一轮任务重新调度。

20. 同一 controller 通过不同模块前缀导入时只注册第一条路径
位置：packages/core/src/register/route/controller.ts:34、packages/core/src/register/module.ts:44
复现：Child 模块分别位于 first 和 second 前缀下时，/first/item 可访问，/second/item 返回 404。
原因：去重只使用 controller 类，不包含继承的模块前缀。
建议：明确同一 controller 的多前缀语义，并按有效路由或 controller+前缀去重。

21. toModule 的构造参数被丢弃
位置：packages/core/src/decorators/module.ts:39、packages/core/src/decorators/injectable.ts:17
复现：toModule(External, { args: ['expected'] }) 创建的 External 实例收到 undefined。
原因：toInjectable 接收 args，但调用 metaSetProviderOnClass 时没有传入。
建议：将参数写入 provider 元数据，并测试实例构造。

22. expectArray 忽略元素检查函数返回的错误
位置：packages/core/src/asserts/expect.ts:70、packages/core/src/register/expect-module.ts:160
复现：expectArray([1], 'bad', () => 'invalid') 不抛错。
影响：调用方依赖返回字符串报告错误的检查失效，例如模块 exports 是否属于 providers 的检查不会生效。
建议：统一谓词的返回契约并处理错误结果，或把调用方全部改为显式抛错。

23. HttpMethod 没有返回装饰器工厂
位置：packages/core/src/decorators/router/http-methods.ts:21
复现：HttpMethod('HEAD') 返回 undefined，因此不能通过公开接口声明自定义 HTTP 方法。
建议：返回 registerRoute(method.toUpperCase())，并测试装饰器注册结果。
